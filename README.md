## Description
This project is a function calling system built around a simple question: can a small, unreliable language model be forced to produce output that is always correct in structure, even when it cannot be trusted to produce it on its own?

Given a natural language prompt, the goal is to identify which function it corresponds to, and extract the parameters that function needs — without ever letting the model produce malformed or unparseable output.

Input: two JSON files — function_calling_tests.json, containing natural language prompts, and functions_definition.json, containing the available function definitions (name, description, parameters, and return type).

Output: a single JSON file where each entry pairs a prompt with the function name and parameters the model selected for it.

The core problem: small language models (this project uses Qwen/Qwen3-0.6B, 0.6B parameters) are unreliable at producing valid structured output through prompting alone — they might succeed only a fraction of the time. Rather than hoping the model gets the format right, this project uses constrained decoding: at every generation step, the model's logits for tokens that would break the expected structure are set to -inf before a token is picked. Since -inf can never be the maximum value among the logits, an invalid token can never be selected — the model is only ever allowed to choose among options that keep the output valid. This guarantees syntactically correct, schema-compliant JSON on every single run, regardless of how unreliable the underlying model is.

## Algorithm explanation

### Core idea: logit masking

At each step, the model gives a score (logit) to every possible next token. Tokens that would break the expected output are forced to `-inf` before picking the best one (argmax). Since `-inf` is always the lowest possible value, a forbidden token can never be chosen — the model can only pick among valid options.

### Step 1 — Choosing the function name

The function name must be one of the names listed in `functions_definition.json`. The algorithm keeps a list of candidate names, and at each step only allows tokens that still match the start of at least one candidate. As tokens are generated, non-matching candidates are removed from the list. Generation stops once only one candidate is left.

### Step 2 — Generating the parameters

Once the function is chosen, each parameter's value is generated the same way, but with rules based on its type:
- **number**: only digits, `.`, and `-` are allowed.
- **string**: anything is allowed except a `"` (which would end the string) or a line break (a sign the model has gone off track).

The fixed parts of the JSON (quotes, colons, commas, braces) are written directly, without asking the model — only the values themselves are generated under constraint.

### Stopping

- The function name stops on its own once one candidate remains.
- A parameter value stops when the model picks a "stop" token (a delimiter for numbers, a closing quote for strings), with a maximum number of steps as a safety limit in case that never happens.
## Design decisions

- **Literal JSON syntax is written directly, not generated by the model.** Characters like `{`, `"`, `:`, `,`, `}` never change regardless of content, so there's no need to make the model "guess" them — they're added directly to the token sequence, leaving only the actual values to constrained generation.

- **Separate rules for `number` and `string`.** The two types don't allow the same characters, so keeping them as two small, independent functions avoids one messy rule with lots of branching, and makes it easy to add a new type later.

- **Different `max_len` per type.** Numbers rarely need more than a few tokens, so a short limit is enough. Strings can reasonably be longer, so they get more room — this limits how far a value can drift off track before being cut off.

- **Pydantic validates all input data.** Every function definition and prompt is checked against a schema before use, catching missing or wrong-typed fields early with a clear error, instead of letting bad input cause a confusing crash later on.

- **Invalid input items are skipped, not fatal.** Validation happens item by item, each wrapped in its own `try/except` — so one malformed entry in a large file is reported and skipped, while the rest of the file still gets processed normally.
## Performance analysis

- **Reliability**: constrained decoding guarantees 100% valid, schema-compliant JSON on every run — the output can always be parsed, regardless of whether the extracted content is semantically correct. This is the core trade-off of the approach: structure is guaranteed, content is not.

- **Accuracy**: around 90% of tested prompts result in the correct function being chosen with correct parameters. Failures mostly fall into two categories: no function in the definitions file actually matches the prompt's intent (e.g. asking for a square root when none is defined), or the model fails to correctly copy a specific value from the prompt (e.g. generating `6.0` as `1.0` in a multiplication).

- **Speed**: processing all test prompts takes approximately **2-minute**, within the 5-minute target. Prompts requiring longer values — particularly large numbers — take more generation steps and are noticeably slower than short ones.
## Challenges faced

- **Special tokenizer characters leaking into output.** Spaces and line breaks are represented internally as special characters (`Ġ`, `Ċ`), which showed up raw in results (e.g. `"Hello\u012034"`). Fixed by replacing them with their real equivalent in `generate_value`.

- **The model drifting into unrelated text.** For string values, the model sometimes kept generating past the intended value. Fixed by treating a generated newline as a stop signal, plus a `max_len` per type as a safety limit.

- **The model copying the wrong value from the prompt.** Sometimes a number would be generated incorrectly even though the right one was in the prompt (e.g. `1.0` instead of `6.0` for "Multiply 6 by 7") — likely due to the model's limited size. Repeating the question before generating parameters was tried as a mitigation, but this remains a known limitation: constrained decoding guarantees valid *structure*, not correct *content*.
## Testing strategy

The implementation was validated by running it against a varied set of natural language prompts and function definitions, then manually inspecting each output for both structural validity and semantic correctness. Testing specifically covered:

- **Large numbers** (e.g. multi-digit sums like `123456 + 987654`), to check that longer values are generated in full rather than truncated.
- **Special characters** in string values (accented letters, `@`, `#`, punctuation), to check the string generation rule doesn't break on uncommon input.
- **Functions with multiple parameters**, including functions with three parameters of the same or mixed types, to check that generation stays consistent across several values in sequence rather than degrading after the first one.
- **Malformed input**: an invalid JSON file, caught and reported without crashing the program.

Each output was checked against the expected JSON schema (correct keys, correct types) and against the intent of the original prompt, to distinguish structural failures (which the constrained decoding approach should make impossible) from semantic ones (the model choosing an imprecise or incorrect value).

## Example usage

```bash
make run
```

This runs the program using the default files in `data/input/` and writes the result to `data/output/function_calling_results.json`.

Sample output (`function_calling_results.json`):

```json
[
  {
    "prompt": "What is the sum of 2 and 3?",
    "name": "fn_add_numbers",
    "parameters": { "a": 2.0, "b": 3.0 }
  },
  {
    "prompt": "Greet shrek",
    "name": "fn_greet",
    "parameters": { "name": "shrek" }
  },
  {
    "prompt": "Reverse the string 'hello'",
    "name": "fn_reverse_string",
    "parameters": { "s": "hello" }
  }
]
```
Every entry pairs the original prompt with the function name and parameters the model selected for it — always valid JSON, as guaranteed by constrained decoding.
